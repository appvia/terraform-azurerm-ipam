## OVERVIEW
Terraform module (azurerm >= 4.14, < 6; terraform >= 1.9) provisioning the Azure Blob backend for the ipam provider/CLI: hardened storage account + private container, and container-scoped RBAC/ABAC that makes storage the permission boundary. Registry: `appvia/ipam/azurerm`.

## CONVENTIONS
- Condition text is whitespace-significant: heredoc indentation, `"\n  OR\n  "` join between pool path tests, `trimspace`/`chomp`. Any reformat changes bytes and breaks the golden test.
- `container_scope` is built from account ID + `var.container_name`, NOT the container's deprecated `resource_manager_id`. Every grant has `depends_on = [azurerm_storage_container.this]`.
- Principal IDs are `for_each` keys: must be known at plan time.
- Checkov skips are inline `#checkov:skip=ID:reason` on the resource (see storage account); `.checkov.yml` has `soft-fail: false`.
- tflint: azurerm + terraform rulesets; every variable/output needs a description and a type; snake_case.
- Comments: `##` heads each resource block, `#` inline; never `//` (terraform_comment_syntax).
- Commits: Conventional Commits, lower-case type, header <= 100 chars (`.commitlintrc.yml`); pre-commit blocks commits to `main`.

## ANTI-PATTERNS (THIS PROJECT)
- NEVER enable `is_hns_enabled`: on ADLS Gen2, renames bypass blob path conditions, and the ipam azblob backend needs a flat namespace.
- NEVER add delete, `add/action`, `move/action` or any management-plane `actions` to the custom role. Environments only overwrite; the platform creates the docs.
- NEVER grant anything at account scope; container scope only.
- NEVER give environments built-in `Contributor`. `builtin` mode (Storage Blob Data Contributor) still leaves `containers/delete`/`write` unrestricted; README documents that warning.
- Don't remove `prevent_destroy` on the account/container: they hold the only allocation record.
- Don't re-enable shared key or local users; callers need `storage_use_azuread = true`.
- Don't make `backend_url`/`provider_config` depend on resource attributes: they configure the ipam provider in the same apply.

## CROSS-REPO COUPLING

Changing condition rendering, role permissions or role names = update the golden files here AND that README in the same change.

## VERIFICATION STATUS
- Proven: `terraform test` plan-mode against a mocked provider; byte-for-byte golden condition comparison. Never applied.
- NOT proven: real Azure enforcement of the RBAC assignments/ABAC conditions; the real aztfauth credential path. Don't claim otherwise in docs or PRs.
- Real check: apply, then `ipam doctor --expect-write <own pool> --expect-no-write <other pool>` as each environment identity.
- Role assignments propagate slowly (minutes). Immediate post-apply writes can see 403; the ipam client handles this with `storage.WithAccessPropagationRetry(ctx)` for writes only. Re-run doctor after a wait before concluding a grant is wrong.
